# Аудит источника данных для «живого» графика («Анализ графиков»)

Дата: 2026-08-05. Проверено на проде (`/opt/moex-strategy-lab-v3`, systemd-юнит `moex-strategy-lab.service`) во время открытой торговой сессии (14:49 МСК, будний день).

## 1. Какой источник используется сейчас

**Бесплатный анонимный MOEX ISS.** Ни ALGOPACK, ни авторизованный real-time ISS, ни брокерский API, ни FAST/SIMBA не подключены и не используются нигде в кодовой базе.

Проверено фактически, не со слов документации:

- `grep -rniE "algopack|api[_-]?key|passport\.moex|MOEX_TOKEN|MOEX_AUTH"` по всем `.py`/`.js` файлам репозитория — **0 совпадений**.
- Файла `.env` на проде **нет** (`EnvironmentFile=-/opt/moex-strategy-lab-v3/.env` в systemd-юните — необязательный, `-` перед путём; файла по этому пути не существует).
- `systemctl show moex-strategy-lab.service -p Environment` — только `PYTHONUNBUFFERED=1`, никаких MOEX-креденшалов.
- Все запросы к MOEX идут через `requests.Session()` без заголовков авторизации (`market_ticker.py:_fetch_snapshot`, `market_data_sync.py:_fetch_page`) — обычный `User-Agent`, ничего похожего на паспорт/токен MOEX.

Вывод: у проекта нет договора с MOEX на real-time данные. Всё, что видит пользователь, — это то, что отдаёт публичный `iss.moex.com` без авторизации.

## 2. Используемые endpoint'ы

| Назначение | Endpoint | Модуль |
|---|---|---|
| Котировки/лента (bid/ask/last/объём/статус торгов) | `GET https://iss.moex.com/iss/engines/stock/markets/shares/boards/TQBR/securities.json?iss.only=marketdata` | `market_ticker.py:_fetch_snapshot` |
| Исторические свечи (все таймфреймы) | `GET https://iss.moex.com/iss/engines/{engine}/markets/{market}/boards/{board}/securities/{ticker}/candles.json` | `market_data_sync.py:_fetch_page` |

Оба — публичные, бесплатные, без ключа.

## 3. Фактически измеренная задержка (не заявленная, а измеренная)

Замер 2026-08-05, открытая сессия, 5 ликвидных тикеров (SBER, GAZP, LKOH, T, YDEX), 45 наблюдений за ~2.5 минуты, 0 ошибок:

- Разница между собственным полем `TIME` бумаги (время последней сделки) и `SYSTIME` ответа MOEX: **стабильно ~900–906 секунд (~15 минут)**.
- RTT сервер↔MOEX: медиана 29.5 мс, среднее 85 мс, p95 275 мс — сама доставка ответа быстрая, задержка целиком в данных, не в сети.

Это стандартная задержка бесплатного/анонимного тарифа MOEX ISS для marketdata, а не техническая проблема или баг. **Мгновенного real-time на бесплатном тарифе не существует физически** — это не вопрос архитектуры фронтенда/бэкенда.

Задержка для исторических свечей (`candles.json`) отдельно не измерялась (не публикуется как отдельная величина у MOEX) — используется только для построения закрытых баров, не для «живой» цены.

## 4. Доступные timestamp'ы

- `TIME` — время последней сделки по бумаге (HH:MM:SS, без даты, МСК wall-clock).
- `UPDATETIME` — время последнего обновления котировки/книги (используется как fallback для малоликвидных бумаг без свежей сделки — иначе индикатор ошибочно показывал бы «нет данных» для бумаги, которая просто не торгуется в этот момент).
- `SYSTIME` — время генерации ответа на стороне MOEX.
- Задержка (`delay_ms`), которую видит пользователь, считается как «время получения ответа нашим бэкендом» минус `TIME`/`UPDATETIME` — **не** как «сейчас» минус `TIME» на клиенте (иначе к задержке MOEX прибавлялась бы задержка сети до пользователя и рассинхрон часов браузера) и **не** через `SYSTIME` MOEX (не доверяем второму стороннему серверу времени — см. `market_ticker.py`, `_fetch_snapshot`).

## 5. Ограничения лицензии и распространения данных

MOEX ISS без авторизации — общедоступный веб-сервис самой биржи, предназначенный для некоммерческого/ознакомительного использования (см. официальные условия ISS на iss.moex.com). Договора на коммерческое распространение котировок нет. Проект не публикует и не ретранслирует сырые данные третьим лицам за пределами собственного UI — используется только для отображения внутри приложения, что укладывается в стандартные условия анонимного доступа. Формальной юридической проверки лицензии не проводилось — это не входит в объём инженерной задачи.

## 6. Что это означает для UI

- Индикатор задержки (`static/realtime-indicator.js`, бэкенд — `market_ticker.get_realtime`) **никогда** не показывает статус «live»/«реального времени» — по построению (`_classify_status`, `market_ticker.py`) минимальный статус при открытом рынке — `delayed`, с честной подписью вида «Данные MOEX · задержка ~15 мин.».
- Возраст последней сделки (`market_time`) и техническая задержка доставки не смешиваются: `market_closed`/`no_trades` показываются отдельно от `delayed`/`stale`/`disconnected`, чтобы отсутствие сделки по неликвидной бумаге не читалось как обрыв связи.
- Порог «предупреждение» (`REALTIME_WARNING_DELAY_MS`, по умолчанию 20 мин) намеренно выставлен **относительно измеренной базовой линии ~15 мин**, а не как универсальное «near real-time» значение — иначе каждая котировка ошибочно помечалась бы как «устаревшая».

## 7. Итоговая честная формулировка источника (используется в UI)

«MOEX ISS · данные задержаны примерно на 15 минут» — при статусе `delayed`/`warning` в торговую сессию; отдельно — «Рынок закрыт · последняя сделка HH:MM:SS» вне сессии; «Источник временно недоступен» — при ошибке запроса к MOEX, без предположений о причине.

Если проект в будущем получит доступ к ALGOPACK или авторизованному real-time ISS, `market_ticker.realtime_config()`/`_classify_status` — единственное место, которое нужно переключить (плюс сам URL/параметры запроса и, вероятно, реальные креды в `.env`/systemd) — остальной пайплайн (форматирование, индикатор, Market Replay-изоляция) уже написан источник-агностично.

См. также `docs/DYNAMIC_MARKET_DATA.md` (архитектура bounded-кэша и пайплайна live-обновлений) и `docs/CHART_ANALYSIS_FIX.md` (несвязанный фикс чёрного экрана графика).
