# Историческое хранилище свечей

Централизованное накопительное хранилище OHLCV-свечей MOEX для модуля графиков
(«Анализ графиков») и Market Replay. Заменяет старый одноразовый CSV-кэш
(`data/chart_cache/`) — тикер/таймфрейм один раз докачивается из MOEX ISS и потом
переиспользуется всеми запросами (любая вкладка браузера, любой воркер gunicorn),
без повторного скачивания всей истории при каждом открытии графика.

## Где хранятся данные

- **SQLite**: `storage/market_data.db` (WAL-режим, короткоживущие соединения на
  каждый вызов — тот же паттерн, что и в `backtests_db.py`/`charts_db.py`).
- Таблица `candles` — свечи: `ticker, board, market, engine, timeframe, ts, open,
  high, low, close, volume, value, num_trades`. Первичный ключ
  `(ticker, board, timeframe, ts)` — естественная защита от дублей: повторная
  докачка пересекающегося диапазона просто ничего не добавляет
  (`INSERT OR IGNORE`).
- Таблица `sync_state` — что и когда докачано: диапазон (`earliest_ts`/
  `latest_ts`), количество свечей, статус, `backfilled_complete` (флаг «вся
  доступная история уже запрошена, дальше назад запрашивать не нужно»).
- Таблица `sync_log` — журнал каждой попытки докачки (для отладки).
- Индекс `(ticker, timeframe, ts)` — быстрые диапазонные запросы без сканирования
  всей таблицы.

Портфельный пайплайн бэктестов (`app.py` / `FILENAME_RE` / `data/*.csv`) **не
тронут** — он остаётся на своих файлах намеренно, чтобы не рисковать уже
проверенным движком бэктеста. Обе системы независимы; при первом запуске старые
CSV (и из `data/`, и из `data/chart_cache/`) один раз импортируются в
`market_data.db` (`legacy_candle_migration.py`, идемпотентно, дедуп через тот же
PK) — история, скачанная раньше, не теряется и не перекачивается заново.

## Таймфреймы

**Нативные** (реально хранятся, качаются напрямую с MOEX ISS): `1m, 10m, 60m, 1d,
1w, 1mo`.

**Агрегированные на лету** (не хранятся отдельно, честно считаются из нативных
свечей той же торговой сессии — `open`=первая, `high`=max, `low`=min, `close`=
последняя, `volume`=сумма): `30m` из `10m`, `4h` из `60m`. Границы бакетов всегда
кратны базовому интервалу, так что бакет никогда не «режет» несуществующую свечу
и не выдумывает данные там, где сессии не было.

Единственный источник правды по таймфреймам — `timeframes.py`
(`NATIVE_TIMEFRAMES`, `AGGREGATE_TIMEFRAMES`, `TIMEFRAME_TO_MOEX_INTERVAL`).

## Тиковые данные

MOEX ISS не отдаёт исторический тиковый архив (сделка за сделкой) через этот вид
интеграции — только агрегированные OHLCV-свечи. `GET /api/market-data/tick-coverage
?ticker=SBER` честно возвращает `{"available": false, "reason": "..."}` для
любого тикера — Market Replay работает по свечам минимального доступного
таймфрейма (1 минута), тики не имитируются.

## API

### `GET /api/chart/history` (и совместимый алиас `GET /api/candles`)

```
?symbol=SBER&board=TQBR&timeframe=10m&from=2026-01-01&to=2026-08-04&limit=5000&before=<unix>
```

Ответ:

```json
{
  "candles": [{"time":..,"open":..,"high":..,"low":..,"close":..,"volume":..}, ...],
  "nextCursor": 1780300000,
  "hasOlder": true,
  "hasNewer": false,
  "actualFrom": 1780300000,
  "actualTill": 1785801600
}
```

Пагинация — курсорная (`nextCursor`/`before`), не offset-based: при прокрутке
графика влево фронтенд передаёт `before=<время самой старой видимой свечи>`,
сервер докачивает недостающий кусок из MOEX (если ещё не докачан и
`backfilled_complete` ещё не выставлен) и отдаёт следующую порцию. Многолетняя
минутная история никогда не уходит одним ответом — верхний предел `limit` жёстко
ограничен на сервере (50–20000).

### `GET /api/market-data/instruments?q=<строка>`

Список инструментов с покрытием по каждому таймфрейму (количество свечей,
диапазон дат, статус, время последнего обновления) — данные для UI управления
загрузкой.

### `POST /api/market-data/sync`

```json
{"tickers": ["SBER","GAZP"], "timeframes": ["10m","1d"], "mode": "initial", "board": "TQBR"}
```

Запускает фоновую job (переиспользует `JobStore` из `jobs.py` — тот же механизм,
что у бэктестов: статус переживает перезапуск сервиса, отменяется кооперативно).
`mode`: `initial` — докачать максимально доступную историю с начала; `continue`/
`update` — докачать только новое с последней сохранённой свечи. Прогресс —
`GET /api/jobs/<job_id>`, отмена — `POST /api/jobs/<job_id>/cancel`.

### `GET /api/market-data/tick-coverage?ticker=<тикер>`

См. «Тиковые данные» выше.

## UI: «Хранилище данных»

Кнопка в шапке приложения открывает модальное окно (`static/market-data-manager.js`):
поиск/фильтр по тикеру, чипсы таймфреймов, режим «Загрузить историю» / «Обновить»,
чекбоксы инструментов, массовый запуск, живой прогресс job, кнопка «Остановить».
Список инструментов и покрытие обновляются после завершения job.

## Как запустить первичную загрузку

1. Открыть «Хранилище данных» в шапке приложения.
2. Найти тикер(ы) поиском, отметить чекбоксами.
3. Отметить нужные таймфреймы (нативные: 1м/10м/1ч/1д/1н/1мес — 30м и 4ч не
   выбираются, они агрегируются автоматически).
4. Режим «Загрузить историю» → «Загрузить (N)».
5. Следить за прогрессом (страница/добавлено свечей на текущем тикере+ТФ).

Обновление уже загруженных данных — тот же диалог, режим «Обновить (докачать
новое)»: подтягивает только то, что появилось на MOEX после последней сохранённой
свечи, без полной перекачки.

## Остановка и продолжение

- «Остановить» в модалке отменяет job кооперативно (проверка между тикерами/
  таймфреймами) — уже докачанные страницы **не теряются**, они сохранены в БД по
  мере поступления (не в самом конце).
- Повторный запуск того же тикера/таймфрейма в режиме `continue` резюмируется от
  последней сохранённой свечи (с сутками нахлёста для безопасности), а не с нуля.
- Если сервис перезапускается посреди job (`systemctl restart`), `JobStore`
  помечает её `failed`/`interrupted` при следующем старте — свечи, уже
  сохранённые до перезапуска, остаются в БД; job можно перезапустить, она
  докачает только недостающий хвост.
- Сетевые ошибки/лимиты MOEX (429, 5xx) — retry с экспоненциальной задержкой
  (`market_data_sync.py`, до 5 попыток на страницу, задержка 1с→2с→4с→8с→16с,
  максимум 30с).

## Ограничения

- Нет исторических тиковых данных (см. выше) — принципиальное ограничение
  MOEX ISS, не временная недоработка.
- Портфельный пайплайн бэктестов не переведён на это хранилище (сознательное
  решение по объёму работ — не хотели рисковать проверенным движком бэктеста
  ради унификации хранилищ).
- Клиентский буфер свечей в Market Replay не обрезается на очень длинных сессиях
  (тысячи+ баров) — см. `docs/MARKET_REPLAY.md` → «Известные ограничения».

## Резервное копирование

`storage/market_data.db` — обычный SQLite-файл, копируется как есть (после
`PRAGMA wal_checkpoint` или простого `sqlite3 .backup`, чтобы не зацепить файл
посреди записи). Проектный скрипт бэкапа копирует всю `storage/` целиком —
см. `deploy/update.sh` и снапшоты в `/opt/backups/moex-strategy-lab-v3/`.
