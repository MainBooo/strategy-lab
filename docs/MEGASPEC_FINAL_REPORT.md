## Что сделано по каждому этапу

**Этап 1.** Инспекция: история раньше хранилась в CSV двумя независимыми
пайплайнами, тиковых данных нет нигде в интеграции MOEX ISS, pip Playwright
не был установлен (использовался MCP-плагин `mcp__plugin_playwright_playwright__*`
весь этот и предыдущие сеансы).

**Этап 2** (`market_data_store.py`, `market_data_sync.py`,
`legacy_candle_migration.py`, `candle_api.py`). Единое SQLite-хранилище
свечей (`storage/market_data.db`) с дедупом по PK, инкрементальная докачка
с retry/backoff/cancel, миграция 572k старых CSV-свечей, новые эндпоинты
`/api/chart/history`, `/api/market-data/*`, UI-модалка «Хранилище данных».
Подробности: `docs/HISTORICAL_DATA.md`.

**Этап 3** (`replay_db.py`, `replay_engine.py`, `static/market-replay.js`).
Бар-за-баром воспроизведение истории без утечки будущих данных
(структурно — через `reveal_index`), ручная торговля (Buy/Short/Sell/Close,
частичное сокращение позиции, усреднение при доливке, авто-SL/TP по
экстремумам бара), undo через step-back, `goto` с honour стопов на всём
прыжке. Подробности: `docs/MARKET_REPLAY.md`.

**Этап 4** (`static/chart-engine/chart-tile.js`, `chart-analysis.js`).
OHLC+изменение в шапке каждого тайла (по наведению курсора), кросс-tile
синхронизация время/масштаб/crosshair по кнопке 🔗, раскладка 3×2 (6
графиков одновременно). Подробности: `docs/CHART_MODULE.md`.

**Этап 5+6** (`scripts/playwright_ui_audit.py`). Автоматизированный прогон
через реальный Chromium по 9 разрешениям (desktop/tablet/mobile) × 15
сценариям: 135/135 проверок чистые (без горизонтального overflow, консольных
ошибок, JS-исключений, HTTP 5xx). Один реальный баг найден и исправлен по
ходу (CSS grid `1fr` без `minmax(0,1fr)`, ещё в Этапе 3), один a11y-фикс
(`display:contents` вместо `display:block` для модалки хранилища данных).
Подробности и разбор false positives самого скрипта: `docs/UI_AUDIT.md`.

**Этап 7** (`tests/test_replay_engine.py` +8 тестов). Закрыты реальные
пробелы покрытия, найденные ревизией существующих 73 тестов: частичное
закрытие позиции (`sell` на часть лотов, пропорциональное распределение
комиссии входа между остающейся позицией и закрытой частью), усреднение
цены при доливке к длинной/короткой позиции, фактический эффект
`slippage_bps` на цену исполнения (в невыгодную для трейдера сторону на
обеих сторонах сделки), отклонение запрещённых переходов состояния
(short-while-long, buy-while-short, sell без длинной позиции). Итого 79
backend-тестов (`pytest tests/ -q`).

**Этап 8** (`scripts/replay_perf_stress.py`). Реальная сессия на SBER/10m
(252k+ баров доступно), 4000 последовательных шагов с несколькими сделками
по пути, измерение через DevTools Protocol `Performance.getMetrics`
(`performance.memory` оказался бесполезен — headless Chromium отдаёт
зафиксированное квантованное значение вместо реального). Результат: JS heap
колеблется в диапазоне ~5-40 МБ без монотонного роста (обычный шум сборщика
мусора, не утечка), число DOM-узлов выросло всего на 32 за весь прогон и
строго привязано к количеству сделок, а не к числу шагов (1000+ шагов подряд
без сделок — нулевой прирост DOM). 0 консольных ошибок, 0 JS-исключений, без
горизонтального overflow. Разбор: `docs/MARKET_REPLAY.md` (раздел
«Ограничения»), сырой отчёт — `test-results/replay-perf-stress.json`
(гитигнорится, локальный артефакт).

## Известные ограничения (сознательные, не баги)

- Тиковые данные недоступны — MOEX ISS не отдаёт исторический тиковый
  архив; минимальный таймфрейм Replay — 1 минута.
- Позиция в Replay — одна нетто-позиция за раз (лонг ИЛИ шорт), прямой
  разворот без промежуточного закрытия не поддерживается.
- Клиентский буфер свечей на графике не обрезается на экстремально длинных
  сессиях (подтверждено безопасным до 4000+ шагов в Этапе 8; сервер всегда
  отдаёт только необходимое, утечки на бэкенде нет).
- Маркировка частичных сокращений позиции на графике — приемлемое визуальное
  упрощение (экономика считается точно на бэкенде, см. `docs/MARKET_REPLAY.md`).
